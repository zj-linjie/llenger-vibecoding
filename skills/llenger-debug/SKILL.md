# Llenger Debug

显式启用本 Skill 时，先在 commentary 中发送一次启动提示：「🔍 已开启 Debug 模式。」；同一任务后续推进时不重复提示。

用户只需提供截图或简短故障描述。主 Agent 负责调查、修复和验收，产物稳定后复用现有 `Reviewer` 独立审查。

## 1. 从现象查证根因

- 阅读项目指令，记录任务开始时的 Git 状态及已有改动。从输入提取实际表现、预期行为和触发条件，区分已观察事实与待验证假设。
- 结合项目上下文定位相关界面、组件、调用链和日志，自主追查，无需用户先指出文件或根因。
- 用复现、日志、失败测试或可核对的代码调用链查证原因。截图只能证明可见现象，不能单独证明根因。
- 判断触发状态是否合法：合法则在应处理它的位置修复；不应存在则追查产生该状态的上游，避免用守卫或重试掩盖错误。
- 两次修复共享同一前提且未通过同一验证时，先写出共同前提，用能区分其真假的观测直接验证，再继续修改。
- 先完成不依赖用户的调查；若关键证据仍缺失，优先询问最关键的一项，例如复现步骤或原始报错。说明已经查到什么以及缺少什么。
- 形成简短诊断记录：**现象、复现方式、根因证据、修复方案、验证方法**，默认写在对话里。明确未能复现的部分及证据边界。
- 证据不足时继续定位或报告阻塞，不把猜测当作已验证的根因。可以先增加诊断日志或失败测试，生产行为的修复应有可核查的因果依据。

## 2. 修复与回归验证

- 主 Agent 完成针对根因的最小充分修复，保留用户已有改动，避免把掩盖症状当作解决问题。
- 优先验证原始触发条件，并按风险检查相邻行为；必要时添加能暴露原故障的回归测试。测试应能发现行为被破坏，并允许保持行为的内部重构；预期结果来自需求，不从被测实现推导。
- 按风险验证真实使用路径、终态和关键副作用；运行验证时确认实际使用的构建或实例包含本次修复，说明构建、单测等检查尚未覆盖的行为。
- 用同一验证方法对照修复前后的结果；无法做前后对照时说明替代证据和局限。清理本次不再需要的临时诊断改动。
- 用户要求先分析或暂不修改时，交付诊断结果，等待其后续指令。无法复现或执行验证时明确报告，不宣称修复已验证。

## 3. 独立 Review

- 修复稳定后调用现有 `Reviewer` 角色；在支持该接口的宿主使用 `agent_type="Reviewer"`、`fork_turns="none"`。复用宿主已配置的角色，不新建或复制角色 TOML，也不依赖 `$team-mode`。
- 交接原始现象、复现材料、诊断证据、仓库路径、本次变更范围与可复核的起点、相关未跟踪文件，以及实际验证结果。将根因作为待审查的结论，允许 Reviewer 质疑它。
- 让 Reviewer 独立检查因果依据、修复正确性、遗漏及回归风险，返回问题位置、证据和严重程度，或明确没有实质发现。Reviewer 只审查；主 Agent 修改源码并负责验收。
- 主 Agent 核实发现并处理阻塞问题，重跑受影响的检查；修正阻塞问题或作出实质修改后，请 Reviewer 复审。尚未解决的阻塞意味着任务未完成。
- 角色或调用能力不可用时，继续可完成的修复与验证，明确报告“独立 Review 未完成”，不能以主 Agent 自查代替独立审查。

## 4. 交付

简短说明现象与根因证据、修复范围、实际执行的验证、独立审查结论和剩余问题；区分确定结论、假设与未验证部分。

默认交付止于本地修改、验证与审查。创建分支、commit、push、PR 或其他外部写入仅按当次用户指令执行；遵守会话里已给出的授权，不重复请求。
