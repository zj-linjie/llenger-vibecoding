# Llenger Feature

显式启用本 Skill 时，先在 commentary 中发送一次启动提示：「🛠️ 已开启 Feature 模式。」；同一任务后续推进时不重复提示。

由主 Agent 贯穿需求讨论、实现和验收；产物稳定后，复用现有 `Reviewer` 独立审查。

## 1. 收敛任务书

- 先阅读项目指令、相关实现与验证入口，记录任务开始时的 Git 状态及已有改动。已有改动属于用户上下文，只修改本任务相关部分。
- 从用户当前目标出发，补齐会影响实现的歧义。先用项目上下文解决可查的问题，再集中询问关键决策；等待回答时继续不依赖答案的工作。
- 形成简短任务书：**目标、范围、实现思路、验收条件、待定事项**。默认写在对话里；用户要求或项目已有约定时再落盘。
- 涉及跨模块变化时，先确认调用方、数据形态和职责归属，优先复用已有扩展点，再确定修改位置；小改动无需额外设计文档。
- 已明确的需求简要收敛后直接推进；影响范围或验收的待定事项解决后再做依赖它们的实现。用户要求先讨论、等待确认或暂不修改时，遵守当前阶段。
- 需求过大时，提出可独立验收的拆分，让用户决定范围；本 Skill 不自动启动其他编排流程。

## 2. 实现与验证

- 主 Agent 按任务书完成最小充分实现，沿用项目约定；不强制拆解任务或增加实现子 Agent。
- 根据验收条件选择必要测试，覆盖实际行为、边界及相关回归风险，优先使用已有入口。测试应能发现行为被破坏，并允许保持行为的内部重构；预期结果来自需求，不从被测实现推导。
- 按风险验证真实使用路径、终态和关键副作用；运行验证时确认实际使用的构建或实例包含本次修改，说明构建、单测等检查尚未覆盖的行为。
- 修正发现的问题，直到实际执行的检查满足验收条件，或存在必须明确报告的阻塞。区分通过、失败和未执行的检查。

## 3. 独立 Review

- 产物稳定后调用现有 `Reviewer` 角色；在支持该接口的宿主使用 `agent_type="Reviewer"`、`fork_turns="none"`。复用宿主已配置的角色，不新建或复制角色 TOML，也不依赖 `$team-mode`。
- 交接任务书、仓库路径、本次变更范围与可复核的起点、相关未跟踪文件，以及实际验证结果。存在已有改动时说明归属，避免把用户原有问题当成本次引入。
- 让 Reviewer 独立核对正确性、需求遗漏与回归风险，返回问题位置、证据和严重程度，或明确没有实质发现。Reviewer 只审查；主 Agent 修改源码并负责验收。
- 主 Agent 核实发现并处理阻塞问题，重跑受影响的检查；修正阻塞问题或作出实质修改后，请 Reviewer 复审。尚未解决的阻塞意味着任务未完成。
- 角色或调用能力不可用时，继续可完成的实现与验证，明确报告“独立 Review 未完成”，不能以主 Agent 自查代替独立审查。

## 4. 交付

简短说明完成的功能与修改范围、实际执行的验证、独立审查结论和剩余问题；未满足的验收条件要明确列出。

默认交付止于本地修改、验证与审查。创建分支、commit、push、PR 或其他外部写入仅按当次用户指令执行；遵守会话里已给出的授权，不重复请求。
