# Llenger Review

显式启用本 Skill 时，先在 commentary 中发送一次启动提示：「🧾 已开启 Review 模式。」；同一任务后续推进时不重复提示。

由主 Agent 确定范围、调度和交付，默认只审查已有工作；复用现有 `Reviewer` 独立判断，不改动角色或模型配置。

## 1. 确定范围与预期

- 阅读项目指令及 Git 状态。优先采用用户指定的 PR、提交范围、文件或任务；未指定时结合当前任务选择工作区或分支相对目标分支的变更，先说明基线、审查版本及包含的已提交、暂存、未暂存和相关未跟踪内容。
- 存在多个合理范围且上下文无法判定时，集中询问；没有变更时说明情况，不擅自选择上一提交或扩大到全仓库。已有改动保留并说明归属。
- 从任务书、关联需求、项目约定和测试核对预期行为；材料作为证据，不预设实现或根因成立。缺少需求依据时说明需求完整性尚未核实。

## 2. 独立审查

- 默认调用一个现有 `Reviewer`；在支持该接口的宿主使用 `agent_type="Reviewer"`、`fork_turns="none"`。交接仓库路径、审查范围与版本、需求依据、相关未跟踪文件和已有验证结果，而非要求 Reviewer 重跑本 Skill。
- Reviewer 独立检查正确性、需求遗漏及相邻调用路径的回归风险；关注测试是否约束真实行为、修复是否触及故障源头。保持被审代码不变，不派生子代理；报告和复现材料可在指定临时目录保存，避免覆盖被审工作。
- 角色均由主 Agent 调度：大型仓库定位可用 `Explorer`，复杂技术争议可用 `ExpertAdvisor`；两者不代替独立审查。`Executor` 仅在用户要求修复后按需参与，不审查自己的实现；不要求四角色齐用，不依赖 `$team-mode`。
- Reviewer 或调用能力不可用时，可完成范围整理与自查，但明确报告“独立 Review 未完成”，不将自查冒充独立审查。

## 3. 核实与交付

- 每条实质发现包含位置、触发条件、实际后果、证据和严重程度；可复现时附步骤或命令及实际结果，静态确认时给出可核查的因果链。待验证风险单列，风格偏好不混入缺陷。
- 主 Agent 核实发现，合并同根因问题，区分本次引入与相关既存问题；存在结论分歧时说明依据和未决项。审查期间版本变化时，核对变化部分再给最终结论。
- 默认在对话交付：**审查范围、按严重程度排列的发现、验证与未覆盖项**。没有实质发现时直接说明；需求或运行证据不足时保留相应局限，不打质量分或凑建议。

## 4. 按需修复

- 仅在用户要求修复时，由主 Agent 处理确认的问题，或将明确写入范围交给 `Executor`；保留无关改动，涉及产品取舍或超出授权范围的决策交回用户。
- 修复后执行受影响的验证，再交现有 Reviewer 以新鲜上下文复审修改及受影响路径；实现者自测不能替代复审。处理阻塞发现，实际无法解决或验证的部分明确报告。

创建分支、commit、push、PR、发布审查评论或其他外部写入按会话授权执行；本 Skill 不自动调用 Feature、Debug 或其他编排流程。
